# Game 2 — The Sprint (alternate-tap race) + champions record

Date: 2026-08-11 · Status: approved

## Problem & Desired Outcome

Post-talk games continue after the RPS rematch. Each game's sole winner earns a reward, so
champions must be recorded per game and survive until the session ends. Game 2 is a race:
every character lines up at the bottom of a top-down track; phones become a two-button
stepper (LEFT/RIGHT must alternate); first to the finish line at the top is the game-2
champion. Expected crowd: 12–18 players. Same characters and names carry over from the talk
demo and game 1 — nobody redraws.

## In Scope

- **Champions record**: the server keeps an ordered list of game champions `{id, name}`,
  recorded when the presenter advances to `winners` with exactly one survivor (the single
  crowning path shared by RPS and the race). Survives everything except `Shift+R`.
  Deck shows the record on game slides (👑 Game 1 — NAME …).
- **`race` phase** in the server phase list. Presenter-driven entry (like all phases):
  entering it revives all players, zeroes race progress, and server-stamps `startsAt`
  (~3.5s countdown — 3, 2, 1, GO on deck and phones).
- **Tap protocol**: phone sends `raceTap {side}`. Server is authoritative: rejects taps
  before GO, from the dead, after a winner exists, and non-alternating sides (each player's
  last foot is tracked server-side; first tap may be either side). A valid tap advances the
  player half a step; `RACE_STEPS = 50` steps to finish (≈100 alternating taps).
- **Phone UX**: two large LEFT/RIGHT buttons; wrong-side tap = error shake + "CAN'T",
  no progress (locally enforced for instant feedback, server enforces for truth); own
  progress readout; countdown; result screen once a winner exists.
- **Deck race view**: top-down track, one lane per living player, avatar tilts
  left/right with step parity (stepping look), finish line on top, live positions from
  snapshots. First to finish → winner overlay → crown → `winners` (records champion).
  Broadcast storm control: race snapshots are throttled (~8/s) rather than per-tap.
- **Race slide** (deck slide 16, after game 1's slide) plus a **`/racing` test route**:
  a standalone page (presenter token required) with join QR, live count, and the race
  view — for testing the race without replaying the whole talk arc. TEST harness only;
  on talk night the race runs from the deck slide with the same characters.
- Late joiners keep working: name gate and untimed draw onboarding extend to the `race`
  phase; a mid-race joiner may tap from zero or wait for the next start.
- Rehearse bots race with randomized tap rates.

## Out of Scope

- Game 3 (format TBD).
- Anti-cheat beyond alternation + GO-gating (two-thumb tapping is legal chaos).
- Persisting champions or drawings across server restarts.

## Acceptance Criteria

1. Game 1 champion crowned → champions list contains them; visible on the deck's game
   slides. `Shift+R` clears it; rematch does not.
2. Presenter opens the race: every phone (including game-1 casualties) shows the stepper
   locked behind a synchronized 3-2-1 countdown.
3. Alternating taps move a character up the deck track; same-side taps shake the phone and
   move nothing (and are rejected server-side if sent).
4. First player to 50 steps freezes the race as winner; later taps do nothing; deck shows
   the champion overlay; crowning records them as game 2's champion — **exactly one**.
5. `/racing?key=<token>` shows QR + count + race controls standalone; a fresh phone can
   join, name, draw untimed, and race. Talk-night flow needs no route change.
6. 18 simulated tappers race without visible stutter on the deck (throttled broadcasts).

## Constraints & Settled Decisions

- One crowning path: champions are recorded only on the `winners` advance with a single
  survivor — RPS and race share it, so the one-winner invariant is structural.
- Server owns race truth (contrast with the deck-owned RPS sim): step counts are pure
  per-player state driven by validated messages, so authority costs nothing and phones
  can't cheat by rendering.
- Phone-side alternation mirrors the server rule purely for latency of feedback.
- Reuse, don't rebuild: onboard flow, QR, WinnerOverlay-style presentation, crown/advance
  controls follow the existing game-slide patterns; 300-line gate applies (track view is
  its own module shared by the slide and `/racing`).

## Validation Evidence

- Unit tests: alternation rule (first tap free, same-side rejected), GO gating, win freeze,
  race entry resets progress + revives, champion recording (single survivor only, no dupes).
- Bot race with ~18 tappers; manual phone walk-through on `/racing`.

## Risks / Open Questions

- Synchronized countdown relies on phone clocks vs the server timestamp (same pattern as
  the 60s draw — was fine); worst case a phone starts a beat late.
- 100 fast taps may trigger browser double-tap zoom on some phones — buttons must set
  `touch-action: manipulation`.
- Reward logistics (what the champions win) is a talk-night concern, not engineering.
