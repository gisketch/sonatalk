# Game 3 — The Gauntlet (rapid-command elimination)

Date: 2026-08-11 · Status: approved (grilled)

## Problem & Desired Outcome

The finale with the best prize: hard, chaotic, fun for 18+ players, ends with exactly one
champion, uses the drawn avatars, and needs zero authored content. Deck fires rapid
commands with shrinking answer windows; wrong or slow = eliminated; last avatar standing
wins. No product branding in-app (same as everything else).

## Grilled Decisions

1. **Content = four procedurally generated categories, no authored questions.**
   - Reflex: `TAP LEFT` / `TAP RIGHT` / `TAP TWICE` / `DON'T TAP` (the trap)
   - Quick math true/false: `7 × 8 = 54` — wrong answers are near-misses (±1–3);
     operand size scales with round number
   - Logic snap: RPS pairings, letter order, odd/even, weekday order — true/false
   - Stroop trick: color word rendered in a different ink — "does the INK match the WORD?"
   All categories resolve to LEFT / RIGHT / both-taps / no-tap, so the phone UI never changes.
2. **Eyes up: prompts render ONLY on the deck; phones are blind controllers.**
   One shared screen = everyone reads at the same instant (per-phone rendering would let
   network delay decide thinking time). Phones show two fat pads + alive/dead + round
   feedback (✓ survived / 💀 out) — tappable without looking.
3. **Presentation:** avatars on a game-show wall at the bottom; prompt slams in huge,
   center-stage, with a visual fuse ring counting the window down; failures drop off the
   wall with a 💀 poof; survivors regroup; winner gets the dancing-avatar overlay + crown.

## Rules (v2 — score attack, settled after dry-run feedback)

- **No elimination.** Everyone answers every round; each correct answer scores +1.
  The first round where NOBODY scores (after round 1) ends the game — top score wins.
  A round cap (30) backstops sharp crowds. Ties → sudden-death rounds among the tied
  leaders only (a splitting round narrows them) until one remains.
- **Auto-run:** one presenter click starts the game; the server loops
  prompt → resolve → results beat → next prompt until a winner exists. No per-round clicks.
- Window: starts 3.0s, shrinks 150ms/round, floor 0.8s. Resolution server-side at close
  (+ grace): `left`/`right` judged on first tap; `double` needs ≥2 taps; `none` = any tap
  misses.
- **Phone pads are contextual** (mode travels in the payload, answers don't):
  - yes/no rounds: red **NO** on the left, green **YES** on the right (YES = `right`);
    first tap **auto-locks** — no fat-finger flips.
  - arrow rounds: free tapping (TAP TWICE lives here), big tap counter + thump animation.
  Locking only yes/no rounds avoids leaking the command type to phone-watchers.
- Winner → crown → recorded in champions (same single crowning path as RPS and the race).
- Mid-game joiners answer from zero score; correct answers stay server-side until the
  results broadcast.

## In Scope

- `gauntlet` phase + server round engine (`server/gauntlet.js`: generator + resolver, pure
  and unit-tested; session stays under the size gate).
- Deck slide 17 + shared stage component; `/gauntlet` test route (same pattern as `/racing`).
- Phone blind-pad screen; rehearse-bot support (random taps, occasional holds).

## Out of Scope

- Authored/crowd trivia (optional future hook), difficulty settings UI, per-player scoring.

## Acceptance Criteria

1. Presenter opens the gauntlet: every connected phone shows pads; deck shows the wall.
2. Each "next command" shows one huge prompt + fuse; at close, wrong/slow avatars drop
   with 💀; phones flash survived/eliminated; DON'T TAP eliminates tappers.
3. Stroop rounds render the word in the wrong ink and resolve on ink-vs-word truth.
4. A full-wipe round eliminates nobody and the game continues.
5. Attrition reaches exactly one player; crown records them as the game's champion.
6. `/gauntlet?key=<token>` runs the game standalone; 18 bots reach a sole winner.

## Display Lag (AirPlay)

The deck is AirPlayed to a TV with a very noticeable (~1–2s) but near-constant delay.
Both timing games compensate with a presenter-calibrated **TV delay offset** (0–2.5s in
250ms steps, deck-local, persisted):

- Gauntlet: `showAt = serverNow + offset` — the answer window opens when the TV actually
  shows the prompt; taps before `showAt` are ignored (spam does nothing).
- Race: `startsAt = serverNow + countdown + offset` — phones and TV agree on GO because
  phones render the countdown from the same stamped `startsAt`.
- Phones never do clock math for pad enablement (server `state` drives it), so phone clock
  skew cannot eat into anyone's window; the server remains the referee.
- Calibration is eyeball-simple: presenter steps the offset until the TV's 3-2-1 lands in
  sync with the phones' buzz during rehearsal.

## Risks

- Room readability: prompt typography must work from the back — huge, one line, fuse ring
  not text. (Presentation, verified at 1280×720.)
- Math generation must never emit an ambiguous truth (validated by property tests).
