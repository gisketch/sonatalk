# WS Core — Session, Join, Phase State Machine

> Derived from [interactive-audience-system.md](interactive-audience-system.md) (grill record).
> Chronologically first: drawing-tier-drops and rps-battle build on this.

## Problem / Outcome

The talk needs a live multiplayer backbone: phones join via QR, the presenter advances a phase
state machine from the deck, and every client renders whatever the current phase says. Without
this, no tier drop, drawing, or battle can exist. Outcome: a boringly reliable session layer
that the later phases only add payloads to.

## In Scope

- One Node process (Express + `ws`) serving the built deck at `/` and the phone client shell at `/join`.
- Server-owned session state: connected players (id, name once set, connection status), current
  phase, per-phase payloads. In-memory only; process restart resets the talk.
- Phase state machine, advanced only by authenticated presenter input (the deck):
  `lobby → names → canvas → tools → drawing → pick → battle → winners → reveal`.
- Phase snapshot broadcast: on every phase change and on every new connection, the server sends
  the full current phase + relevant payload. Late joiners land in the current phase with no
  special-casing. Clients render purely from the latest snapshot.
- Deck join beat: QR display (stable VPS URL, generated ahead of time) + live "N connected"
  counter at the deck's bottom edge.
- Deck state mirror: deck retains every received player/name (later: drawing, pick) locally so
  a WS drop never erases already-received state.
- Bail hotkey on the deck: swaps slide 7 to the existing fake simulator at any point, no visible error.
- Presenter identification: deck connects with a presenter token (env/query secret) so only it
  can advance phases or kick players.

## Out of Scope

- Drawing canvas, tools, uploads (drawing-tier-drops spec).
- RPS pick, battle sim, winner/reveal content (rps-battle spec).
- Reconnection/resume, persistence, accounts, chat. A refreshed phone is a new anonymous join.
- Horizontal scaling, TLS termination (Nginx Proxy Manager on the VPS provides TLS + the edge).

## Acceptance Criteria

1. Phone scans QR → `/join` loads on iOS Safari and Android Chrome → deck counter increments
   within ~1s; closing the tab decrements the roster (counter may show total joined vs live —
   pick one and keep it consistent).
2. Presenter advances `lobby → names` → all connected phones show the name input within ~1s;
   submitted names appear on the deck roster; duplicate names accepted verbatim.
3. A phone joining mid-arc receives the current phase immediately (e.g. joins during `names`
   → sees name input, not a blank lobby).
4. Killing the server mid-arc: deck keeps all mirrored names; bail hotkey lands on the fake
   simulator with no error UI; restarting the server yields a fresh empty session.
5. Only a client with the presenter token can advance phases; a phone sending a phase-advance
   message is ignored.
6. 30 concurrent phone connections sustained through a full phase walk with no dropped
   snapshots (multi-tab harness evidence).

## Constraints & Settled Decisions

- Server owns truth for everything phones can affect; deck is authoritative only for its local
  battle rendering (later spec).
- Snapshot-on-change over event deltas for control state; volumes are tiny (~30 clients).
- Hosting: VPS "bedrock", exposed as talk.gisketch.com via Nginx Proxy Manager — no tunnels,
  direct WSS through the proxy. Pre-tasks: verify VPS health; create the NPM proxy host with
  WebSocket support enabled and TLS; capture the stable URL for the QR asset.
- WS heartbeat: server pings each socket (~30s) and phones answer, so idle connections survive
  nginx proxy read timeouts without any reconnect logic.
- Phone client shell lives in the same Svelte/Vite project (multi-page or route split) so design
  tokens and the 300-line gate apply everywhere.
- All transitions presenter-driven; no timers in this layer (the 60s timer belongs to drawing).

## Validation Evidence

- Multi-tab harness: scripted walk of the full phase machine with 10+ simulated phones, output
  of roster/phase logs.
- Own-device test over the real talk.gisketch.com QR (mobile data, not venue wifi).
- Failure drill artifact: notes/recording of the kill-server + bail rehearsal.

## Risks / Open Questions

- Venue internet is a single point of failure for live mode (accepted; mirror + bail mitigate).
- Nginx proxy idle timeouts can silently drop quiet WebSockets: mitigated by the 30s server
  heartbeat (settled above). Verify with a 10+ minute idle phone through talk.gisketch.com
  early; only if drops persist does a minimal transparent WS re-open become justified.
- Counter semantics (live vs total joined) — trivial, decide at implement.
